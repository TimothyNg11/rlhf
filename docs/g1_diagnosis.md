# G1 diagnosis: the entropy blow-up is an uncorrected rollout–training mismatch

## Symptom

Our from-scratch GRPO run tracks the TRL reference closely for ~50 iterations
(reward EMA within 0.03, near-identical response lengths), then entropy climbs,
generations run away (mean length 300 → 1700 tokens), and reward collapses
(0.66 → 0.33). TRL, on the **identical** config and reward function, stays flat
(entropy 0.18 → 0.11) through the full run. A parity run that kept zero-variance
groups at advantage 0 (TRL/DeepSeek style) blew up *earlier*, ruling that
difference out.

## Root cause

Completions are generated by **vLLM** (bf16 kernels, paged attention) but the
"old" log-probabilities are recomputed with the **HF training forward** (a
deliberate design choice — the plan requires never using the sampler's
logprobs). vLLM and HF produce slightly different token probabilities for the
same weights (different kernels, precision, attention impl). Our probe metric
`sampler_recompute_logprob_diff` measured this gap the whole time (~0.006/token).

Because old-logprobs come from HF, the PPO ratio π_θ/π_old is HF-over-HF and
captures only gradient drift — **not** the vLLM↔HF backend gap. The completions
were actually drawn from the vLLM distribution, so treating the HF recompute as
the behavior policy leaves an uncorrected off-policy bias. It is tiny per token
but systematic, and it compounds over tokens and steps into the entropy
explosion. This is precisely the failure the recent literature documents.

The clincher: TRL's `GRPOConfig` defaults `vllm_importance_sampling_correction =
True`, so our TRL **reference** run was silently applying the correction while
our trainer was not. Same algorithm, one missing term.

## The fix: truncated importance sampling (TIS)

Reweight each token's policy-gradient term by a truncated ratio of the two
behavior policies:

    w_t = min( exp(old_logprob_HF − sampling_logprob_vLLM), C )

applied as a **stop-gradient** coefficient on the PG term only (the KL penalty
is a separate regularizer and is left unscaled — matching TRL's ordering). The
cap is one-sided (the ratio may fall below 1 freely, but is bounded above at C)
to trade a little bias for bounded variance. C = 2.0 (verl's typical 1.5–5.0).

Implemented as `grpo_math.trainer.algo.truncated_is_weights` +
`grpo_microbatch_loss(..., tis_weight=...)`, wired through the loop from the
sampler logprobs already captured on each `RolloutSample`. Config knobs
`train.use_tis` / `train.tis_cap`; metrics `tis_weight_mean` / `tis_capped_frac`.

## References

- Yao et al., 2025 — *Your Efficient RL Framework Secretly Brings You Off-Policy
  RL Training* (TIS as the fix for the rollout/training gap).
- verl docs — *Mathematical Formulations of Rollout Correction Methods*
  (the min(ρ, C) formula, C ≈ 1.5–5.0).
- *Defeating the Training-Inference Mismatch via FP16* (arXiv 2510.26788) and
  *On the Rollout-Training Mismatch in Modern RL Systems* (NeurIPS 2025) — the
  mismatch causes entropy collapse/instability; correcting it restores stability.
- *Group-Relative REINFORCE Is Secretly an Off-Policy Algorithm* (arXiv
  2509.24203) — why GRPO tolerates but must correct for off-policy data.
- TRL `GRPOConfig.vllm_importance_sampling_correction` (default True) — the
  correction our reference run used and our trainer initially omitted.

## Validation status

TIS is implemented, unit-tested (formula, PG-not-KL scaling, identity when
disabled), and committed. The prediction to confirm on GPU (~$3, one G1 rerun
with `configs/g1_100.yaml` on the current code): entropy should now stay
controlled like TRL's rather than exploding at ~iter 55, and the curves should
track past the previous divergence point.
